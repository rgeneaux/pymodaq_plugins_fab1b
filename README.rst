pymodaq_plugins_maranax
=======================

PyMoDAQ 5.2 plugin for Andor Marana-X cameras using the native Andor SDK3
``atcore`` API.

This project is intentionally independent of PyLabLib for acquisition. The
camera is configured through SDK3 features and images are acquired using the
native AT_QueueBuffer / AT_WaitBuffer interface.

Current status
--------------

* Native SDK3 ctypes wrapper.
* Native SDK3 circular buffer.
* Mono16 zero-copy NumPy view of the SDK buffer.
* One controlled copy from the SDK buffer into a PyMoDAQ-owned frame buffer.
* Dedicated acquisition thread.
* ROI and exposure control.
* Continuous/live acquisition.
* Basic frame-rate and dropped-frame accounting.

The current implementation deliberately uses Mono16 as the acquisition
encoding. Mono12Packed conversion can be added once the exact Marana-X
firmware/SDK combination has been tested.

Installation
------------

Install the package in editable mode in the same environment as PyMoDAQ::

    pip install -e .

Install the Andor SDK3 software supplied with the camera. The ``atcore.dll``
must be discoverable by the process, or its full path can be selected in the
PyMoDAQ settings.

The code has not been tested against every SDK3 release. Verify the installed
SDK3 version and the Marana-X firmware before using it for unattended
acquisition.

Performance design
------------------

The acquisition path is::

    Marana-X -> SDK3 -> preallocated native buffers -> AT_WaitBuffer
              -> NumPy view -> PyMoDAQ-owned frame -> dte_signal

The SDK buffer is returned immediately after the copy. It is therefore never
held by the GUI. The PyMoDAQ-facing frame has independent ownership.

For maximum acquisition throughput, keep processing out of the Qt slot
connected to ``frame_ready``. A future high-throughput recorder should consume
the acquisition frames in a separate producer/consumer queue.

Chopped pump-probe with a slow chopper
--------------------------------------

``DAQ_1DViewer_MaranaXChopperTA`` is for a chopper whose period spans many laser shots (e.g. 10 Hz on a 1 kHz
laser). Each single-shot frame is classified pump-on/off from its hardware timestamp and a chopper phase fitted on
the data (contrast of the *Reference pixels*), so the shot parity plays no role. Use it in *Chunked* mode with
*Vertical binning*; *Measure background* (probe blocked, pump on) is subtracted per pump state.

Delay Binner (chunks) extension
-------------------------------

Builds a (delay x pixel) map of dR/R or ΔOD while a delay stage oscillates: a 0D detector measuring the delay
(fs, any plugin giving a timestamped 0D value) and the ``MaranaXChopperTA`` viewer run independently, and every
shot of every chunk is binned at the delay interpolated at its own time, in a pump-on or pump-off average. The
chunk-averaged observable cannot be used because the stage keeps sweeping while a chunk is acquired. The extension
switches on the viewer's *Output single shots* setting while it acquires (see ``chopper_shots.py``); *Create
Viewer* adds a 2D viewer module giving the map (snap during *Snap duration*, or continuous grab).

The extension targets PyMoDAQ 5.2. After adding it, reinstall once (``pip install -e .``) so that PyMoDAQ finds
the ``pymodaq.extensions`` entry point. Things to set: *History* must be longer than one chunk, *Latency* is the
delay between a delay measurement and the timestamp of its data, *Max gap* the longest hole in the delay
measurements across which shots are still given a delay.

Piezo with a waveform
---------------------

``DAQ_Move_PI_Waveform`` is the PI actuator of ``pymodaq_plugins_physik_instrumente`` (E-754 and other GCS2
controllers) with a *Waveform* group that sweeps the stage periodically, as a **triangle** (default: constant speed,
every delay visited equally often) or a **sine**. The sweep is defined in pump-probe delay units, for a
retroreflector (1 fs of delay = c/2 = 0.1499 um of stage):

* *Time zero position* (um): where the stage is at zero delay (*Use current position* sets it);
* *Delay min* / *Delay max* (fs): the ends of the sweep, e.g. -20 and +40;
* *Delay increases with*: the direction of the axis;
* *Rate set by*: type either the *Speed* (fs/s) or the *Frequency* (Hz), the other one is computed (speed =
  2 x delay span x frequency; for a sine, the mean speed);
* optional rounding of the triangle corners, and a number of cycles (0 = until stopped).

The motion is generated by the controller's wave generator, so it is hardware timed and no command is sent while it
runs. A sweep leaving the travel range of the axis (or the bounds of the module) is refused before anything moves.
Any move command, the stop button and closing the module stop the sweep. If PyMoDAQ stops abruptly the controller
keeps sweeping until it is stopped (*Stop waveform*) or powered off.
